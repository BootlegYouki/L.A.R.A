# Org Split Implementation Plan

> **For agentic workers:** Executed by one Sonnet worker in an Orca chat (the Lead's rule: no Agent tool, no Codex). Steps use checkbox syntax. Do the tasks in order.

**Goal:** Create four fresh private repos in the GitHub org `L-A-R-A-National-High-School` (`lara-server`, `lara-desktop`, `lara-mobile`, `lara-context`) from the current `staging` snapshot of `BootlegYouki/L.A.R.A`, wired so each app repo's agent reads the shared repo and the sibling repos and files issues instead of waiting.

**Architecture:** Fresh `git init` per repo from `git archive` of tracked files (no history). Server owns `contracts/`, `scripts/mock_hub.py` and the contract tests. `lara-context` is nearly blank (team folders plus a draft design system). Each app repo carries the same slim `AGENTS.md`, `lara-context` skill, SessionStart hook script and issue template.

**Tech Stack:** git, `gh` CLI, bash, Python 3 (`unittest`), existing app stacks (unchanged).

**Spec:** `docs/superpowers/specs/2026-11-23-org-split-design.md`

## Global Constraints

- Org: `L-A-R-A-National-High-School`. Repo names exactly `lara-server`, `lara-desktop`, `lara-mobile`, `lara-context`. Visibility: private. Default branch: `main`.
- Source is the tracked files at `HEAD` of branch `staging` in `/home/youki/github/L.A.R.A` (use `git archive`, never copy the working tree: it has `node_modules`, `target`, untracked files and a dirty diagram edit).
- No history, no CI (`.github/workflows` not carried), no PR template, no CODEOWNERS, no branch protection.
- Never edit the old repo or push to it. Never add Claude as author or add `Co-Authored-By`/"Generated with" lines to any commit (user's global rule). Commits are authored by the git user already configured.
- `CLAUDE.md` is a symlink to `AGENTS.md` in each app repo.
- An agent never edits another team's repo; it files an issue with label `cross-repo`.
- Do NOT do: archive the old repo, re-file the 3 open issues, repoint `lara-watch.service`. Those wait for the Lead's OK (Task 6).
- Scratch work in `/tmp/claude-1000/-home-youki-github-L-A-R-A/896bc1fa-c758-4fed-b492-0377273faa04/scratchpad/split/` (call it `$WORK`); final clones live in `/home/youki/github/` next to each other as `lara-server`, `lara-desktop`, `lara-mobile`, `lara-context` so sibling lookup works.

## Review Focus

- Hook with no network or no `gh` login: prints one line, exits 0, session unaffected.
- Hook when a sibling has local uncommitted work or diverged history: `pull --ff-only` fails, prints "skipped <repo>: not fast-forwardable", does not touch the work.
- Repo cloned under a different folder name or siblings missing: hook clones missing ones into the parent folder; never fails the session.
- Contract tests pass from the new `lara-server` root (path assumptions: `contracts/`, `scripts/mock_hub.py`, `tests/hub_client.py` all at repo root).
- A second developer's fresh `gh repo clone` of one app repo gets a working hook with no local setup beyond `gh auth login`.

### Task 3: App repo files (identical set for server, desktop, mobile)

**Interfaces:**

- [ ] **Step 1: `AGENTS.md`** (short, under ~40 lines; the builder writes the wording). Must contain: L.A.R.A in 3 lines (offline classroom platform for Philippine public schools: Hub, mobile app, desktop app); the four-repo map with the org URL; "Read `lara-context` (sibling `../lara-context`) before starting work and whenever the task touches another team or a doc might exist"; "Before building something that depends on another repo, read that repo. Do not include the old invariants or rules.
- [ ] **Step 2:** `ln -s AGENTS.md CLAUDE.md`.
- [ ] **Step 3: `lara-sync.sh`** (bash, `set -u`, never `set -e`). Behavior: parent = parent of repo root; for each of `lara-context lara-server lara-desktop lara-mobile` other than this repo: if `$parent/<name>` exists run `git -C ... pull --ff-only` under `timeout 10`, on failure print `skipped <name>: could not fast-forward`; if missing run `timeout 60 gh repo clone L-A-R-A-National-High-School/<name> $parent/<name>`, on failure print `skipped <name>: not cloned (no network or gh login)`. Then print `lara-context changes (7 days):` followed by up to 5 lines of `git -C $parent/lara-context log --since=7.days --name-only --pretty=format:%s` summary, and `Open cross-repo issues here:` followed by `gh issue list -l cross-repo -L 5` output (silently nothing if gh fails). `exit 0` at the end, unconditionally.

- [ ] **Step 5: skill `lara-context`**: description says to load it at the start of any task, and whenever work touches another team or a doc may exist. Body: where siblings live (`../lara-*`), what to read first (`lara-context/README.md`, then your team folder and `shared/`), how to scan another repo (read only; look at its `AGENTS.md`, `docs/`, and `contracts/` in `lara-server`), how to file an issue: `gh issue create -R L-A-R-A-National-High-School/<repo> -l cross-repo -t "<title>" -F <body file>` using the template fields (what I need, why, route/screen/file involved, what I already checked, link to any doc in `lara-context`), and the rule to put long write-ups in `lara-context/<team>/` and link them.
- [ ] **Step 6: issue template** `cross-repo.md` with those same fields.
- [ ] **Step 7: Verify the script** from each snapshot: `cd $WORK/<repo> && git init -q && bash .claude/hooks/lara-sync.sh; echo "exit=$?"` must print `exit=0`. Then `PATH=/usr/bin:/bin` with `gh` hidden (e.g. `env PATH=$(dirname $(command -v bash))`), run again and expect `exit=0` and "skipped" lines.
