# 3.2.4 Implementation Plan

L.A.R.A. is proposed for deployment in a public school in the Philippines, with one pilot class of about 40 Learners. Deployment uses a dedicated L.A.R.A. Hub (server) and a classroom Wi-Fi network so that core classroom activities remain available without an external network connection. The process is designed for a short setup and subsequent operation by the school's designated Admin. The relative-week schedule below is a proposed sequence, not a record of agreed calendar dates or completed deployment.

| Relative period | Activity | Responsible role(s) | Proposed duration |
|---|---|---|---|
| Week 1 | Install Hub, verify classroom-network access, configure Admin PIN and Teacher accounts | Developers and Hub Admin | Within Week 1 |
| Week 1 | Orient Teachers on classroom and assessment workflows | Developers and Teacher | Within Week 1 |
| Week 2 | Install access applications and complete registration/enrollment | Developers, Teacher and Learners | Within Week 2 |
| Weeks 3–4 | Conduct pilot classroom activities and monitor issues | Teacher, Learners and Hub Admin | Two weeks |
| Week 5 | Administer evaluation instruments and organize collected data | Developers and Teacher; participating Learners as applicable to the approved method | Within Week 5 |
| Weeks 1–5 and handover | Perform USB backups and hand over routine support | Hub Admin, assisted by Developers | Throughout the pilot |
| If classes are suspended | Optionally enable approved remote access | Hub Admin, assisted by Developers | As required; outside pilot evaluation |

**1. Hub installation and network preparation.** The Developers assist the Hub Admin in installing the L.A.R.A. Hub on the dedicated server computer using the supported Windows or Linux package. The setup provides the local runtime dependencies and required network configuration. The L.A.R.A. Hub connects to the classroom Wi-Fi router by Ethernet cable; if more rooms need coverage, additional access points are cabled to the same router and set to access-point mode so that all devices stay on one local network. The team verifies that the Hub is reachable from a separate device on the classroom network before proceeding. Installation is described as a short setup; no installation-time result is assumed.

**2. Administrative setup.** The Hub Admin establishes the administrative PIN and creates Teacher accounts. The Admin checks the Hub's network status and records the local address needed for application installation. Administrative functions remain separate from the classroom functions available to Teachers and Learners.

**3. Teacher orientation.** The Developers demonstrate class creation, sharing of class codes, approval of enrollment requests, posting of materials and assignments, homework review, quiz administration, gradebook use and export. Orientation covers both the Mobile app and Desktop app because Teachers have the same classroom capabilities on both devices. Teachers are also shown how saved resources and queued work behave when the Hub is unavailable.

**4. Access-application installation.** Learners join the classroom Wi-Fi and obtain the Mobile app from the Hub's local download portal. The same portal distributes the Desktop app for available laptops and school computers. Installation guidance is provided locally so that the process does not require a public application store or an external network connection.

**5. Registration and class-code enrollment.** Learners register with the required identity information and PIN, then enter the class code shared by the Teacher. The Teacher reviews each pending request and grants or declines access. Enrollment approval is checked before classroom materials and activities become available.

**6. Pilot classroom operation.** The Teacher uses the system for lesson distribution, announcements, assignments and paperless quizzes. Learners access saved lessons outside the classroom and prepare permitted work offline. On reconnection, queued work is synchronized with the Hub. Developers record operational issues for investigation while preserving classroom records.

**7. Evaluation activities.** The Developers and participating Teachers arrange the approved evaluation activities after classroom use. These include the Teacher usability questionnaire and software-quality evaluation, together with technical and task-based observations specified in the study's data-collection method. The printing allowance does not determine the final participant sample. Outcomes, scores and measurements are reserved for Chapter IV.

**8. USB backup and handover.** The Hub Admin performs routine backups using the Hub's backup function and stores the resulting backup archive on USB storage. The Developers demonstrate the supported restore procedure and distinguish a system backup from a gradebook export. The handover covers account maintenance, network-status checks, routine backup and escalation of technical issues.

**9. Optional Remote/Suspension Mode.** If classes are suspended, the Hub Admin may enable the approved opt-in connection to the same Hub. It retains the existing account and access rules and can be disabled when no longer needed. This option is available for continuity but is not part of the proposed pilot evaluation.

After the pilot, the Hub Admin manages accounts, monitors the Hub and maintains backups. Teachers continue to manage their classes through the access applications. Issues outside routine administration are referred to the Developers through the support arrangement established at handover. No continuous availability or support response time is claimed.
