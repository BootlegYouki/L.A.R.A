# 3.2.3 Development and Testing: Desktop App

The proposed Desktop app is developed through a contract-first process that coordinates it with the Hub and Mobile app. Native desktop capabilities are combined with a web-based interface, local persistence and bilingual presentation. The selected technologies are summarized below; the version numbers identify the reproducible dependency snapshot used to describe the development method.

| Technology | Version | Purpose |
|---|---|---|
| Tauri | 2.12.5 native framework | Native application shell and desktop integration |
| React | 19.3.1 | Component-based interface |
| TypeScript | 5.9.3 | Strict static type checking |
| Tailwind CSS | 4.3.3 | Styling integrated with the shared design tokens |
| Vite | 6.4.5 | Development tooling and production bundling |
| Tauri SQL plugin | 2.6.0 | Local SQLite access and migrations |
| Zustand | 5.0.16 | Application state and nonsecret preferences |
| Vitest | 3.2.7 | Unit testing |
| ESLint | 9.39.5 | Static code-quality checks |

*Table 3.x. Technologies selected for Desktop app development.*

Tauri uses the operating system's webview rather than packaging a separate browser engine, supporting a smaller installer than Electron-based applications. The selected approach does not establish a measured installer size or memory consumption. React provides the presentation components, while TypeScript supplies static checking at development time. Network responses additionally require runtime validation because static types do not validate received data.

The interface uses the shared L.A.R.A. design system and the prototype as its visual reference. Nunito fonts and Phosphor icons are bundled locally. Colors, controls, navigation and wording follow the approved design rules, including English and Filipino presentation. SQLite provides local classroom storage; application preferences are separated from protected account credentials. Migration and access tests check consistency with the common client-data definitions.

Development begins with shared definitions of requests, responses, events and stored records. The team implements one issue at a time, reusing established state and data-access patterns. Network-dependent work is first exercised against a mock Hub that supplies reference behavior. Integration then connects the Desktop app to the real Hub on the classroom network. Each change is submitted for review before it enters the shared integration branch.

| Testing activity | Proposed method |
|---|---|
| Static checks and production build | Run lint and strict TypeScript checks, then create the production interface bundle; the standard build command is **npm run build**. |
| Unit tests | Use Vitest to check state transitions, validation, loading/error states, language selection and relevant service behavior. |
| Local data integrity | Use isolated synthetic databases to check migrations, foreign keys, account-scoped queries and preservation of queued records after reopening. |
| Mock-Hub integration | Exercise discovery, account access, enrollment and synchronization against the mock Hub; check expected responses and error handling. |
| Real-Hub integration | Repeat the supported workflows on the classroom network and compare behavior with the shared interface definitions. |
| Offline and interruption tests | Start with the Hub unavailable, reopen saved resources, interrupt transfers or quiz participation, reconnect and verify that permitted queued work is retained and acknowledged. |
| Desktop UX and accessibility audit | Compare screens with the prototype; inspect keyboard access, visible focus, control sizes, contrast, loading/empty states, both languages and enlarged text. |
| Representative-device checks | Observe startup, interaction, video playback and resource use on the available school computers and laptops; record hardware and operating-system details with the measurements. |

*Table 3.x. Proposed Desktop app development and verification activities.*

Classroom integration includes operation with the router's external-network connection unplugged. Unit tests alone do not establish the behavior of native database permissions, credential storage, media access or operating-system webviews, so these boundaries are also exercised in the native application. Browser rendering checks do not substitute for a native launch. Testing uses synthetic records and avoids real Learner credentials or personal data.

The desktop UX audit forms part of the final evaluation stage. It checks the desktop control dimensions, text contrast, consistent iconography and layout behavior at different window sizes and text scales. Observations on each available operating system are identified separately; success on one platform is not treated as evidence for another. Functional pass rates, performance figures, usability scores and implementation results are reported in Chapter IV.
