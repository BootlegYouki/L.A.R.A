# 3.2.3 Development and Testing — Desktop Application

The desktop client employs modern web technologies wrapped in a lightweight native application shell to achieve cross-platform compatibility across Windows, Linux, and macOS while maintaining a minimal memory footprint suitable for aging school computer laboratory hardware. This section documents the technology stack, development methodology, and testing strategies applied to ensure functional correctness, offline resilience, and accessibility compliance.

## Technology Stack

The desktop application is built using the following verified technology versions, as recorded in `desktop/package.json`:

**Application Framework:** Tauri 2 provides the native desktop application shell, embedding a platform-specific WebView (WebView2 on Windows, WebKitGTK on Linux, WKWebView on macOS) to render the React user interface. Tauri's architecture avoids bundling a full Chromium instance, resulting in installer sizes under 15 MB compared to Electron's typical 120 MB footprint. The framework exposes a secure Inter-Process Communication (IPC) bridge allowing the JavaScript frontend to invoke Rust commands for database operations, network discovery, and secure credential storage.

**Frontend Framework:** React 19.3.1 serves as the declarative UI library, with functional components and hooks managing application state and side effects. The component hierarchy follows a pages-and-components organization where top-level page components (e.g., `HomePage.tsx`, `StreamPage.tsx`) compose reusable UI components (e.g., `ClassroomCard.tsx`, `TopAppBar.tsx`).

**Type Safety:** TypeScript 5.9.3 with `strict: true` compiler flag enforces static type checking throughout the codebase, eliminating implicit `any` types and requiring explicit null/undefined handling. This compile-time safety reduces runtime errors from API response mismatches and state management bugs. Contract types (e.g., `SyncPullResponse`, `ClassroomDetail`) are validated using runtime guard functions (`isSyncPullResponse`) at the network boundary to safely narrow `unknown` JSON payloads to typed interfaces.

**Styling:** Tailwind CSS 4 provides utility-first styling with design tokens imported from the L.A.R.A. design system (`design-system/desktop/tailwind.theme.ts`). Custom CSS variables define the color palette (primary green, secondary purple for AI features, status colors), typography (Nunito sans-serif font family), border radii, shadow depths, and spacing scale. Responsive breakpoints adapt the layout between laptop (1366×768) and desktop (1920×1080) display sizes.

**State Management:** Zustand 5 implements a lightweight global store (`useAppStore`) for application-level state including authentication status, selected Hub connection, cached classroom list, and UI language preference (English or Filipino). The store follows immutable update patterns and integrates with React's reconciliation to trigger efficient re-renders.

**Database:** The `@tauri-apps/plugin-sql` version 2 plugin provides type-safe access to the local SQLite database (`lara_client.db`) stored in the application's data directory. Numbered migrations (`src-tauri/migrations/001_client_offline.sql`) are applied automatically on first launch, ensuring schema consistency. Foreign key constraints are enforced on every connection via `PRAGMA foreign_keys = ON`, validated through automated tests.

**Build System:** Vite 6.4.1 serves as the development server and production bundler, leveraging native ES modules for instant hot module replacement during development. The production build performs tree-shaking, code splitting, and minification to optimize bundle size and initial load time.

**Additional Libraries:** Vitest 3 provides unit testing capabilities, ESLint 9 enforces code quality rules, and the Phosphor icon library supplies consistent iconography throughout the interface, with files bundled from `design-system/assets/phosphor/` to avoid external CDN dependencies.

## Development Methodology

**Contract-First Development.** The desktop team implements features strictly according to the OpenAPI specification (`contracts/openapi.yaml`), WebSocket event schemas (`contracts/events/`), and client database schema (`contracts/schema/client_offline.sql`) maintained in the repository root. No route, event, column, or error code is added in application code before it exists in the contract and the mock Hub serves it. Proposed changes to contracts are escalated to the Lead Developer for separate `contract-change` pull requests that merge before dependent feature work begins.

**Mock Hub Development.** All network-dependent features are developed and tested against the Python mock Hub simulator (`scripts/mock_hub.py`) rather than the real Rust backend. The mock implements the complete REST API, WebSocket event bus, and UDP discovery beacon, serving hardcoded but realistic responses from seed accounts (teacher `T-0001`, enrolled learner `123456789012`, unenrolled learner `123456789013`, all with PIN `1234`, class code `K7M4QX`). This parallel development model allows the desktop and mobile teams to make progress while the server team builds the Hub's Rust implementation, converging at scheduled integration milestones where clients switch to the real backend.

**Sprint-Based Development.** Work is organized into six time-boxed sprints aligned with the Agile model described in section 3.1.1. Each sprint has defined feature goals (e.g., Sprint 1 focuses on discovery and authentication, Sprint 2 on class enrollment and synchronization), and concludes with an integration day where all three teams test against the shared staging branch. Within each sprint, both desktop developers collaborate on a single GitHub issue, implementing it to completion with tests and documentation before proceeding to the next issue in sequence.

**Pull Request Review.** Every feature implementation is submitted as a pull request to the `staging` branch, where the Lead Developer reviews it against a mandatory checklist: contract alignment, mock Hub parity, build and test passage, offline state handling, bilingual string coverage, accessibility token compliance (40px buttons, 48px tabs, 56dp quiz options), secret redaction, and team documentation updates. Pull requests that fail any checklist item are rejected with specific feedback. Only approved pull requests merge to `staging`, and only fully integrated sprints merge from `staging` to `main`.

**Offline-First Architecture.** Every screen is designed to function without an active Hub connection by reading from the local SQLite mirror. Network requests are treated as refresh operations that update the cache and trigger UI re-renders, but never block the initial view. When the Hub is unreachable, a dismissible banner displays "Hub offline — viewing saved data" while the screen continues to display cached content. User actions that require server confirmation (e.g., creating a class, posting an announcement) are disabled with explanatory helper text while offline, or queued with `QUEUED_FOR_SYNC` status (e.g., homework submissions, quiz attempts) and uploaded automatically upon reconnection.

## Testing Strategy

**Build Verification.** The command `npm run build` in the `desktop/` directory executes TypeScript compilation (`tsc --noEmit`) followed by Vite production bundling (`vite build`). The TypeScript compiler must exit with zero errors, catching type mismatches, missing imports, and contract violations at compile time. This check runs on every commit via continuous integration and must pass before pull request approval.

**Unit and Integration Tests.** Vitest tests in `desktop/tests/` verify service modules (`services/db.ts`, `services/api.ts`, `services/sync.ts`), state management logic (`store/app.ts`), and type guard functions (`services/types.ts`). Database tests use Node.js's built-in `node:sqlite` module to validate schema migrations, foreign key constraints, and query logic. API tests mock fetch responses to verify error handling, token attachment, and response validation. Synchronization tests confirm atomic cursor updates and reset behavior without requiring a live Hub.

**Mock Hub Integration.** Feature tests launch `scripts/mock_hub.py` in a subprocess, perform the full application workflow (discovery, authentication, class join, synchronization, content viewing), and verify that the expected data appears in the UI and local database. These tests run in the repository's shared test suite (`python -m unittest discover tests`) and validate that the desktop client correctly implements the contract.

**Offline Scenario Testing.** Developers manually test offline behavior by starting the application with the Hub running, loading class data, stopping the mock Hub process, and confirming that screens continue to display cached content without errors or infinite loading spinners. Actions requiring network connectivity are verified to show appropriate disabled states or offline queuing behavior. The Hub is then restarted to confirm automatic reconnection and synchronization of queued work.

**Accessibility Compliance.** [DESKTOP 6.1] The planned Sprint 6 desktop UX audit will verify that all interactive elements meet minimum size requirements: 40px for buttons and icon buttons, 48px for navigation drawer items and tabs, 56px for primary actions and quiz option buttons. Color contrast ratios between text and backgrounds will be measured to confirm WCAG AA compliance (4.5:1 for normal text, 3:1 for large text). Loading states will be audited to ensure that skeleton screens and progress indicators are present with descriptive ARIA labels for screen reader users. Keyboard navigation and focus visibility will be tested to confirm that all workflows are operable without a mouse.

**Production Device Testing.** The desktop application will be installed on representative hardware including student laptops with Intel Celeron processors and 4 GB RAM, and older Windows 10 school computer laboratory PCs. Launch time, page transition smoothness, and video playback performance will be measured to identify bottlenecks. Memory consumption will be profiled using browser developer tools to ensure the application remains under 200 MB resident set size during typical usage.

## Testing Limitations and Scope

This section documents the development and testing **methodology**; empirical results (pass rates, performance measurements, usability scores) are reserved for Chapter IV: Results and Discussion. The testing strategy ensures functional correctness and robustness during development, but field validation with actual teachers and learners occurs during the Sprint 6 pilot evaluation described in section 3.2.4.

The desktop team does not possess physical access to macOS hardware during the development phase, so macOS-specific testing (keyring credential storage, WebKit rendering, application signing) remains unverified until the platform packages are built and tested by external collaborators or postponed to post-defense releases.
