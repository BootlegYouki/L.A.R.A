# 3.2.4 Implementation Plan

The deployment of L.A.R.A. at the pilot school follows a structured nine-step process designed to minimize technical complexity and maximize teacher autonomy. The implementation prioritizes a rapid "Day 0 Deployment" timeline where the Hub becomes operational in under three minutes from installer launch, with no command-line operations or internet connectivity required.

## Deployment Steps

**Step 1: Hub Installation on School PC.** The school's ICT coordinator or designated administrator executes the L.A.R.A. Hub installer (`.exe` for Windows or `.deb` for Linux) on the dedicated always-on school PC. The installer performs the following automated operations: installs the WebView2 runtime if absent on Windows systems, deploys the Hub application to the system program directory, creates desktop and Start menu shortcuts, and registers Windows Firewall inbound rules for TCP ports 8080 (HTTP REST and file server), 8081 (WebSocket events), and UDP port 8888 (network discovery beacon). On Linux systems, the post-installation script similarly configures `ufw` or `firewalld` rules where those firewalls are active. The entire installation completes in under three minutes with no manual configuration.

**Step 2: Administrative Account Setup.** Upon first launch, the Hub presents an initial setup screen prompting the administrator to create a 4-digit PIN. This PIN secures the Hub's administrative console, which provides account management, network port health monitoring, USB gradebook export, and database backup functions. The administrator then creates teacher accounts by entering each teacher's full name and employee ID, generating 4-digit PINs for their initial sign-in.

**Step 3: Teacher Orientation.** [ASK LEAD: Confirm person responsible for teacher orientation and duration.] The participating teachers receive training on the L.A.R.A. system's core workflows: creating classroom sections and generating 6-character class codes, approving learner join requests from the pending queue, posting announcements and uploading PDF handouts and MP4 videos, creating assignments with due dates and point values, building and scheduling timed quizzes, grading homework photo submissions, and exporting gradebook data to USB flash drives. Teachers are oriented to both the desktop client (for use on school laptops) and the mobile client (for on-the-go access from their personal Android phones), as both interfaces provide identical teacher functionality.

**Step 4: Learner Application Installation.** Learners connect their personal Android smartphones to the classroom Wi-Fi network and navigate to `http://<hub-ip>:8080/download` using any web browser. The Hub's captive download portal displays the Hub's local IP address on its dashboard for easy reference. The portal serves the L.A.R.A. Student APK with a three-step visual installation guide: (1) tap the large "Download L.A.R.A. (Android)" button, (2) when prompted by the Android browser, tap Settings and toggle on "Allow from this source" to permit installation from unknown sources, and (3) tap Install, open L.A.R.A., and proceed to self-registration. Learners using school computer laboratory PCs or personal laptops similarly download the desktop installer (`.exe` or `.deb`) from the same portal.

**Step 5: Class Code Enrollment.** Learners launch the installed application and complete self-registration by providing their full name, 12-digit Learner Reference Number (LRN), and a self-chosen 4-digit PIN for subsequent sign-in. After authentication, learners enter the 6-character class code provided by their teacher (displayed as `XXX-XXX`, for example `K7M-4QX`). This action places the learner in a pending approval queue visible to the teacher, who reviews the request and taps either "Accept" or "Decline." Upon approval, the learner gains immediate access to the class stream, materials, assignments, and quizzes.

**Step 6: Pilot Classroom Operation.** [ASK LEAD: Provide pilot deployment dates and duration.] During the pilot period, teachers utilize L.A.R.A. for regular classroom instruction, posting lesson materials, assigning homework, and administering paperless quizzes. Learners access content both during school hours over the classroom Wi-Fi and at home in offline mode using their locally cached data. All homework submissions, quiz attempts, and private comments created offline are queued with `QUEUED_FOR_SYNC` status and automatically synchronize upon reconnection to the Hub. The pilot validates the system's offline-first architecture, multi-device synchronization accuracy, and pedagogical utility under authentic classroom conditions.

**Step 7: Survey Administration.** [ASK LEAD: Confirm survey administration timeline, method (paper or digital), and responsible person.] At the conclusion of the pilot period, participating teachers complete the System Usability Scale (SUS) questionnaire and the ISO/IEC 25010 software quality evaluation instrument. Learners provide feedback through task completion observations and time-on-task measurements recorded during quiz sessions. These data collection activities generate the empirical evidence required for the thesis evaluation chapter.

**Step 8: USB Backup Routine.** The administrator establishes a regular backup schedule using the Hub's built-in USB export function. Inserting a USB flash drive into the Hub PC and selecting "Backup Database" from the administrative console writes a timestamped copy of the master `lara.db` SQLite file and all uploaded media to the removable drive. This backup protects against data loss from sudden power failures or hardware malfunctions, and provides a portable gradebook archive for school record-keeping systems.

**Step 9: Optional Remote/Suspension Mode.** [ASK LEAD: Confirm whether Remote/Suspension Mode will be enabled during the pilot, and if so, provide the timeline and responsible person.] If classroom access is interrupted by inclement weather or institutional suspension, the administrator may optionally enable Remote/Suspension Mode from the Hub dashboard. This feature runs a Cloudflare Tunnel as a managed child process, exposing the Hub's REST and WebSocket services at a stable HTTPS subdomain (e.g., `hub-<school>.lara.app`). Learners and teachers can then continue accessing the full system—stream, materials, assignments, quizzes, and the AI tutor—from their homes using the same accounts and bearer tokens. Remote quiz timing operates with local countdowns anchored to the Hub's authoritative `started_at` timestamp, maintaining fairness without the classroom LAN's live tick-by-tick synchronization. When school resumes, the tunnel is disabled and all operations revert to local area network access.

## Post-Pilot Support

Following the pilot evaluation, the school administrator retains full operational control of the Hub through the administrative console. Routine support responsibilities include resetting forgotten teacher or learner PINs, creating new teacher accounts for additional faculty, monitoring network port health status, and performing regular USB backups. The administrator does not require programming expertise or internet connectivity to maintain the system. Technical issues beyond the administrator's scope are escalated to the development team through documented support channels established during the pilot orientation.

The Hub's design ensures that classroom instruction can continue uninterrupted even if the development team is unavailable, as all core features—authentication, synchronization, content delivery, quiz administration, and AI tutoring—operate autonomously on the local area network without external dependencies.
