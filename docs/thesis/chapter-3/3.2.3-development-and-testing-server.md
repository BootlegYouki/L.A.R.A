# 3.2.3 Development and Testing: Hub Component

The proposed Hub is developed through a contract-first workflow that coordinates its classroom services with the Mobile app and Desktop app. The development method combines iterative implementation, automated verification, and classroom-network integration. The technologies selected for the Hub are summarized below.

| Technology | Version | Purpose |
|---|---|---|
| Rust | 1.98.1, stable | Hub application logic and native services. |
| Axum | 0.8.9 | HTTP request handling and file-transfer operations. |
| Tokio | 1.54.1 | Concurrent network operations and asynchronous tasks. |
| SQLx | 0.9.0 | Database access, connection pooling, and migrations. |
| SQLite | SQLite 3, bundled through SQLx | Authoritative local classroom storage. |
| Tauri | 2.12.5 | Native Hub Admin window and application packaging. |
| tokio-tungstenite | 0.30.0 | WebSocket communication. |
| Python | 3.11 for continuous integration | Mock Hub and shared verification tools. |

*Table 3.x. Technologies selected for Hub development.*

Development begins with the shared definitions of requests, responses, events, and database records. The mock Hub provides reference behavior while the clients and Hub are developed in their sprint sequence. Each team completes one issue through a pull request. The Lead reviews changes before they enter the shared staging branch. Integration activities then connect both access applications to the Hub through an isolated classroom network.

Automated verification covers database integrity, authentication and classroom access, file transfers, synchronization, objective grading, and AI lockout. Rust unit and integration tests are executed with **cargo test**. Shared contract and mock tests use **python3 -m unittest discover tests**, while an offline and localization guardrail checks the architectural constraints. Continuous integration applies these checks to pull requests. Classroom integration additionally checks operation with the router's WAN cable unplugged, Hub unavailability, local persistence, disconnection, and successful reconnection.

The planned stress test assumes a L.A.R.A. Hub server with a four-core processor of Intel Core i5 class, 8 GB RAM, an SSD, and Linux. The Hub is wired to one consumer dual-band Wi-Fi 5 router whose WAN cable is unplugged. A load script on two laptops generates 40 simulated clients. Five real devices, comprising three Android phones and two laptops, are used to check the Mobile app and Desktop app during the run. This arrangement is an assumed test setup and does not represent completed field testing or a respondent sample.

| Planned scenario | Procedure | Acceptance target |
|---|---|---|
| Simultaneous quiz submission | Forty simulated Learners submit a quiz at the same moment. | Every submission is recorded within 300 ms, with 100% correct scores. |
| Simultaneous homework upload | Forty homework photos of approximately 800 KB each are uploaded at once, including submissions queued offline and delivered after reconnection. | All expected uploads succeed and their records are retained. |
| Concurrent video and stream access | Ten devices stream a lesson video while 30 browse the stream. | Playback continues without failure and the per-client cap of 2 MB/s is maintained. |
| Mid-quiz disconnection | Ten devices are disconnected from Wi-Fi during a quiz and then reconnected. | Answers are preserved and queued work synchronizes after reconnection. |
| Concurrent tutor requests | Ten Learners ask the tutor at once. | Queue positions are shown, and the Learner currently being served receives the first word in under 2.5 seconds. |

*Table 3.x. Planned stress-test scenarios and acceptance targets.*

Each scenario is run five times under the assumed setup. Response times and success counts are collected from the load script logs. Hub CPU and RAM use are observed through htop and sar, and a database check confirms that every expected record exists. The checks compare recorded scores, submissions, and queued work with the expected outcomes of each scenario. The AI evaluation precedes model selection, and the chosen model is assessed on the Hub hardware.

Measured response times, resource use, success rates, evaluation scores, and test outcomes are reported in Chapter IV. The exact SQLite engine version is also recorded there from the built Hub.
