# 3.2.3 Development and Testing: Hub Component

The Hub development method uses a shared contract to coordinate the Rust application, the Hub Admin window, and both access applications. The following technology inventory separates declared dependency ranges from versions resolved in the committed lockfiles. A Rust language edition, a library binding version, and a compiler or database-engine version are distinct records and are not treated as interchangeable.

The contract-first workflow begins with the routes, message schemas, naming rules, and database definitions in `contracts/`. A shared-interface change requires a separate contract-change PR with matching mock behavior and contract tests before feature work depends on it. The mock Hub supplies the reference behavior for the Mobile app and Desktop app while corresponding Rust features are developed. Work proceeds by the documented sprint steps, with one issue and one PR for the team at a time. Branches originate from `staging`; the Lead reviews PRs targeting `staging` against the architectural invariants before integration. This manuscript PR uses the explicit Chapter III documentation exception to normal folder ownership.

The Hub uses SQLx migrations to reproduce the authoritative database and connection options to enable write-ahead logging, foreign-key enforcement, normal synchronization, and the documented busy timeout. A visible data change and its `sync_revisions` entry belong in the same transaction. Role and class-access checks protect operations, and separate response representations prevent Learner answer-key disclosure. These design properties define verification targets rather than observed test outcomes in this chapter. The current Rust quiz and synchronization route modules are scaffolds; their presence alone is not evidence that assessment and synchronization behavior is complete.

| Verification activity | Method and intended evidence | Implementation boundary |
|---|---|---|
| Rust unit tests | `cargo test` in `server/backend/` exercises the available module tests, including database connection settings, schema parity, stable Hub identity, rollback, revision ordering, and discovery serialization. Failures are associated with the affected invariant. | Existing tests are located in Hub modules; the technical specification also identifies tests planned for later features. |
| Rust integration tests | The tests in `server/backend/tests/` start the real Hub using a temporary data directory and test ports. Existing cases cover startup, HTTP/WebSocket scaffolding, the portal, database identity, and installer/firewall consistency. | These tests establish the scope of existing automated checks and do not establish completion of planned routes. |
| Contract and mock checks | `python3 -m unittest discover tests` checks the contract, schema, and mock behavior. The default run uses the mock Hub; it must not be described as a complete test of the Rust implementation. | `tests/test_contract_coverage.py` and the rest of `tests/` provide shared acceptance references. |
| Architectural guardrail scan | `python3 scripts/verify_invariants.py` checks the repository's offline and localization rules. Findings are reviewed against the changed files. | The scan supplements behavioral tests and cannot establish physical-device performance. |
| Build and CI review | Local Hub checks use `cargo check --all-targets` and `cargo test`. On PRs targeting `staging` or `main`, CI runs shared contract and guardrail checks; changed-area detection gates the Hub job, which runs Clippy, Rust tests, the Hub UI build, and the Tauri check. | A documentation-only PR can skip the Hub build job; a skipped job is not evidence of a new application build. |
| Sprint integration | On integration day, the access applications use the real Hub on `staging` with the router's WAN disconnected. Classroom flows, Hub-unreachable behavior, queued work, reconnection, and preservation of records are checked; deviations become issues. | The workflow prescribes this activity; no completed field session is asserted here. |
| Planned 40-device stress test | The `[SERVER 6.1]` activity examines concurrent Hub operation with 40 connected devices, using the PRD's classroom workloads and targets. Quiz submissions and grade records, simultaneous homework transfers, disconnection and reconnection, media delivery, and AI queue behavior where available are examined against their documented requirements. | This is a planned technical load, not a respondent count or a completed experiment. The approved workload and apparatus remain to be specified. |

The planned stress procedure assesses the PRD's submission reliability, synchronization latency, transfer success, and disconnection-resilience requirements under concurrent use. It also considers the documented bandwidth cap and preservation of authoritative quiz and homework records. The AI feasibility evaluation precedes model-dependent functionality and evaluates the selected candidates on the actual Hub; no particular model or measured capacity is presumed. Test logs, performance observations, evaluation scores, and pass or failure results belong in Chapter IV. This section specifies the development and verification method without reporting those outcomes.
