# 3.2.3 Development and Testing: Mobile App

Mobile development follows the descriptive-developmental research design and Agile (Scrum-based) iterative model in Section 3.1.1. Sprint 0 through Sprint 6 organize the shared foundations, classroom functions and evaluation. The native Android application combines a declarative interface, local persistence and bilingual presentation. Table 3.x summarizes the selected technologies and the recorded dependency versions.

The application supports a minimum of Android 8.0 (API 26), targets Android 15 (API 35), and is tested on Android 14. Budget phones with 3 to 4 GB RAM provide the representative hardware environment. The chosen software stack supports local operation and does not require external classroom services. CameraX and Media3 are selected for the camera and video functions; no version is attributed to either framework before its dependency is incorporated.

Development begins with shared definitions of requests, responses, events and stored records. Features are first exercised against a mock Hub that supplies reference behavior while the three teams work in parallel. Each team completes one assigned task through a reviewed pull request before integration. At sprint boundaries, the Mobile app connects to the real Hub on the classroom network. Review findings guide refinements in the next iteration.

The architecture separates Compose screens and ViewModels from domain interfaces, repositories, Room persistence and network operations. Screens observe locally stored data. Synchronization updates the mirrored records and their sequence position in one transaction. Supported offline actions remain saved on the device until the Hub confirms receipt. A broken connection therefore does not require discarding completed classroom work.

| Testing activity | Proposed method |
|---|---|
| Automated tests and static checks | Run the standard Mobile verification command, **./gradlew test lint**, to execute local unit tests and Android lint. Run the shared contract tests and offline/localization checks as part of integration. |
| Emulator and mock-Hub integration | Exercise manual connection, account access, role navigation, malformed input, cancellation and unreachable-Hub states. Emulator behavior does not establish real-phone broadcast discovery. |
| Real-phone integration | Repeat discovery, classroom navigation, camera, video and submission workflows on an Android 14 phone; record the model, RAM and operating-system details. |
| Offline classroom operation | Unplug the router's external-network connection while retaining classroom Wi-Fi and exercise enrollment, resources, homework and quizzes. |
| Airplane-mode and home-study checks | Download resources, enable airplane mode with Wi-Fi off, restart the application, open saved content and retain supported work for later delivery. Reconnect and check for acknowledgment without duplication. |
| Quiz interruption and recovery | Begin while connected, save answers, disconnect and complete locally; repeat after application interruption. Check reconstructed timing, preserved answers, submission receipts and hidden tutor controls. |
| Camera and media checks | Inspect captured-photo orientation and JPEG size below 800 KB; stream video with seeking, download it and replay it offline. Check that decoders and capture resources are released. |
| Persistence and privacy | Interrupt synchronization and retry queued work; verify transactional consistency, account-scoped access and preservation of unsynchronized records. Inspect Learner data for excluded answer keys and private credentials. |
| Accessibility and localization | Review English and Filipino screens, visible status explanations, loading and empty states, contrast and text scaling. Measure 52 dp minimum controls and 56 dp primary actions and quiz options. |
| Classroom-scale integration | Coordinate 40 simultaneous quiz submissions and homework uploads with the Hub and Desktop app; compare expected and recorded receipts and grades. |

**Memory and battery profiling.** Resource evaluation uses a physical phone with 3 to 4 GB RAM. Android Studio profiling and Android memory diagnostics record heap use during document access, video playback, camera compression, upload and Hub-assisted tutoring. The application heap must remain below 250 MB without out-of-memory failures. Phones below 6 GB RAM do not load a local model. Emulator measurements are not substituted for budget-phone evidence.

Battery observations record the device, Android version, battery condition, screen brightness, workload, network state, duration and vendor power-management settings. Repeated runs examine battery change and the reliability of background synchronization after disconnection and reconnection. Consistent operating conditions support comparison, while vendor process restrictions and observed failures remain part of the record. Battery findings are reported as measured observations rather than assumed compliance with an unspecified numeric target.

Verification records identify the command or procedure, hardware conditions, expected behavior, observed outcome and limitations. Physical-device checks supplement unit tests because automated results alone do not establish camera behavior, discovery reliability or resource consumption. Measured memory use, battery change, timings, success rates and evaluation scores are reported in Chapter IV.
