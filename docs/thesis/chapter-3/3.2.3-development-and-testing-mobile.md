# 3.2.3 Development and Testing: Mobile App

Mobile development follows the descriptive-developmental research design and Agile (Scrum-based) model in Section 3.1.1. Sprint 0 through Sprint 6 organize the shared foundations, classroom functions and evaluation. This section describes the development baseline and planned verification procedures. It does not report completed field trials, device measurements or usability outcomes; those findings belong in Chapter IV.

**Development procedure.** Shared contracts define request and response formats, events and local records before implementation. Mobile features are developed against the mock Hub rather than waiting for the production Hub. The emulator reaches the development computer through `10.0.2.2`; real phones use the classroom network. Each issue is implemented in a focused branch and reviewed through one team pull request before integration into `staging`. The shared contracts and mock behavior are verified before an interface change is used. At sprint integration, the same workflows are checked against the real Hub.

The planned architecture separates Compose screens and ViewModels from domain interfaces, repositories, Room persistence and network operations. Screens observe local data. A synchronization pull applies records and its integer `next_cursor` atomically; supported offline writes remain `QUEUED_FOR_SYNC` until the Hub confirms receipt. This design is an implementation requirement, not a claim that the current discovery scaffold contains the complete offline system.

**Automated verification.** The Mobile team runs `./gradlew test lint` from `mobile/` to check local unit tests and Android lint. On Windows the corresponding wrapper is `gradlew.bat test lint`. The repository checks are `python3 -m unittest discover tests` and `python3 scripts/verify_invariants.py`. These checks examine shared contract behavior and offline/localization constraints. The procedure includes testing ViewModel state transitions, malformed addresses, timeouts and cancellation, then adding persistence, migration, synchronization and quiz tests as those components are implemented. A command is not evidence of a passing run unless its output is recorded.

| Test setting or scenario | Planned procedure | Evidence and criterion |
|---|---|---|

| Mid-quiz disconnection and restart | Begin while connected, change answers, disconnect, continue the local countdown and complete; reconnect and inspect the receipt. Repeat after app interruption. | Saved answers, timer reconstruction and receipt; no lost completion or premature display of held scores. Tutor chat remains absent throughout an active attempt. |

**Resource and battery profiling.** The planned `[MOBILE 6.1]` activity measures the app on physical phones with 3 to 4 GB RAM. Android Studio profiling and `adb shell dumpsys meminfo org.lara.app` provide memory evidence during document access, video playback, camera compression, upload and Hub-assisted tutor use. Heap usage is compared with the below-250 MB target, and out-of-memory events are recorded. Phones below 6 GB RAM must not load a model locally. Emulator measurements cannot establish compliance on budget hardware.

Battery testing records the device model, Android version, battery condition, screen brightness, workload, network state, duration and vendor battery-optimization settings. Repeated runs compare battery change and background synchronization behavior under consistent conditions, including reconnection and vendor process restrictions. These are proposed measurement controls, not completed measurements.
