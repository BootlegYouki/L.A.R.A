# Teacher approvals - MOBILE 2.4 (#51)

## Scope and contract

The independent 2.4 implementation at `d140e77` includes final 2.3 (`adade1a`) and the merged #192 contract change from staging. This 2.5 branch integrates it with the shared sync session; 2.4 PR #191 remains independently reviewable in the approved order.

The teacher loads classes with authenticated `GET /api/classrooms`. Each roster row from `GET /api/classrooms/{id}/roster` supplies the required canonical `enrollment_id`; `POST .../approve` and `POST .../reject` produce the existing learner events. No enrollment ID is generated by the client.

## Key files and data flow

- `TeacherApprovalSession` starts a class-list refresh whenever foreground Hub reachability returns, after HELLO, and on join events. The panel subscribes even when the class cache is empty. Pending class-code hints are retained until a newly fetched class mounts its roster model, so an event cannot disappear just because its class was not cached yet.
- `SavedRosterRefresher.refreshClasses` fetches REST classrooms and atomically upserts their metadata. `refresh` saves roster profiles and enrollments with the returned server IDs in a Room transaction. Account/role/class ownership and duplicate/secondary-key checks reject stale or inconsistent writes. Missing wire timestamps use the observation time; they are never a sync cursor. Known creation/join metadata is preserved where the response omits it.
- `RosterViewModel` observes saved rows, opens the sheet for matching join hints, updates optimistically, rolls back failed commands and refreshes the REST roster after a decision. A successful decision is not reversed just because its follow-up refresh fails. Offline actions are disabled.
- `TeacherApprovalPanel` is mounted only in the teacher graph. Lifecycle/background disposal stops the socket and refresh subscriptions. Expired sessions return to sign-in without deleting saved/queued work.

Teacher controls show only unarchived classes owned or co-taught by the signed-in teacher. The Hub remains the authorization boundary.

## Learner unlock through canonical sync in 2.5

The learner's own `GET /api/classrooms` supplies request titles/status notices, but 2.5 grants class access only through canonical enrollment rows filled by sync. `LearnerClass` requires an enrollment identity. The independent 2.4 REST access stopgap is removed in this branch as requested by the Lead in issue #52.

The learner UI reads canonical rows through `RoomEnrollmentRepository`. Only an ACTIVE enrollment with no restrictive saved notice permits Open class. A receipt or an ACTIVE event alone cannot grant access; the event requests authenticated refresh and sync. Sync reconciles request notices atomically with its page/cursor. Teacher-only roster identifiers/LRNs are never sent to a learner.

The old `rest_class_access:<user-id>` keys are cleared when Room opens on upgrade. No production reader/writer remains. Existing enrollments, cursors, request notices and queued work are preserved; there is no destructive migration or schema change.

## UI and failure states

English and Filipino strings remain paired. Both class panel and sheet use pulsing loading skeletons. Accept is 56dp minimum; Decline and Cancel are at least 52dp. Dark-green actions meet contrast requirements, with a white sheet and 50% navy scrim. Title, message and roster scroll together while Cancel stays in a fixed footer, including Filipino at 200% font size. The optional all-pending-list redesign is not required for this flow; the existing sheet reviews one learner at a time.

Offline caches remain readable without a blocking dialog. REST failures leave the old snapshot intact; all page writes are transactional. Cached and queued work is never cleared or migrated destructively.
